# 后端云部署与 Dify 联调

目标是保持原 FastAPI + SQLite 后端和原 Dify 应用，不增加独立前端。公网地址由托管平台为部署成功的服务生成；它不是本机 localhost，也不是手工填写一个域名就能生效。

## 部署配置

通过 Railway 服务配置指定 `order_api/Dockerfile`、启动命令 `python -m order_api.serve` 和健康检查 `/health`。平台已弃用 railway.json/railway.toml，本项目直接通过服务配置部署，不使用已弃用配置文件。容器读取平台 `PORT`，使用一个进程和一个副本。启动前验证工具密钥、操作员密钥和持久磁盘，数据库可写并初始化成功后才开启服务。

服务需要挂载一个持久卷到 `/data`；数据库位于 `/data/logisupply.db`。Railway 自动提供 `RAILWAY_VOLUME_MOUNT_PATH`，生产入口会拒绝未挂卷或把数据库写到卷外的配置。服务工作目录保持仓库根目录，不能设成 `order_api`，因为知识文档在 `docs/`。

| 云端环境变量 | 配置 |
|---|---|
| LOGISUPPLY_DB_PATH | `/data/logisupply.db` |
| LOGISUPPLY_TOOL_API_KEY | 独立随机工具密钥，至少24个ASCII字符 |
| LOGISUPPLY_ADMIN_API_KEY | 另一独立随机操作员密钥，不提供给 Dify |
| LOGISUPPLY_PUBLIC_URL | 平台生成的服务 HTTPS 地址 |
| PORT | 使用平台提供的值；本机默认8018 |

密钥只通过平台环境变量配置，不能提交 Git、写进 Dockerfile 或上传本地 `dify/local/`。每次发布只上传代码、模拟订单和 SOP；已有测试数据库、原应用备份、截图和本地密钥不进入镜像。新云端数据库使用四条演示订单初始化。

健康检查为 `/health`。生成公开域名时将服务目标端口设为实际 `PORT`。此时 `/tools/*` 仍要求 `X-API-Key`，`/admin/*` 仍要求独立 `X-Admin-Key`。

## Dify 接入与真实验收

1. 先检查公网 `/health`，再用鉴权请求验证订单查询和 SOP 工具。
2. 更新原 `LogiSupply V2 物流工具` 的 Swagger `servers[0].url` 为部署地址，保留工具 provider ID 和 `X-API-Key` 鉴权。
3. 在原应用环境变量中更新 `ORDER_API_BASE`，保持 `LOGISUPPLY_TOOL_API_KEY` 与云端一致。
4. 预览订单查询、异常分析和草稿生成，核对执行日志中工具返回成功，不能只看工作流绿色标志。
5. 发送当前草稿完整确认短语，核对真实工单号；重复发送后应返回同一工单。
6. 使用操作员接口推进 processing、resolved、closed，在原聊天中分别查询进度。
7. 重启云端服务后再次查询，确认挂卷中的工单和事件仍存在。
8. 上述通过后发布原 Dify 应用并复验 Web App。

自动验收脚本为 `python evaluation/cloud_acceptance.py`，需要在进程环境设置上表的地址、两类密钥及 `DIFY_API_KEY`。脚本真实调用云端后端和已发布的 Dify API；会创建并关闭两条模拟工单，只有全部通过才写出 `evaluation/results/cloud_acceptance.json`。

该脚本不能代替服务重启后的持久化检查；重启后需另查它记录的实际工单号。若中途失败，不得把先前成功报告当作本次成功证据。
