# 本机运行（保留 Dify，模型允许 API）

当前应用和数据库都在本机：React 静态页面由 FastAPI 提供，FastAPI 调用本机 Dify 1.17.1；Dify 的经典 Agent 调用同一个 FastAPI 的业务工具。订单、草稿、工单和网页会话在本机 SQLite，制度向量在本机 Milvus 3.0.2。Qwen3-14B 与 BAAI/bge-m3 仍通过 SiliconFlow API 调用，因此需要联网并可能产生模型调用费用。

## 启动、使用、停止

本机已配置 Windows PowerShell、Python 3.13、WSL 的 Ubuntu-24.04 和其中的 Docker Compose。首次复制到另一台电脑时需要这些运行环境；首次下载镜像和安装官方插件可能较久。不要同时启动两套占用相同端口的副本。

在项目根目录执行：

```powershell
# 第一次安装 Python 开发依赖时增加 -Install，日常启动无需重复安装
.\start-local.ps1 -Install
.\status-local.ps1
.\stop-local.ps1
```

日常启动为 `.\start-local.ps1`。脚本会准备私有配置、构建并启动容器、连接 Milvus、初始化或更新本地 Dify 工作流，并显式检查/构建 SOP 索引。已有账号、服务密钥、应用 ID、业务库和向量库会保留，不需要每次重新配置。

| 入口 | 地址 | 用途 |
| --- | --- | --- |
| 用户工作台 | http://127.0.0.1:8020 | 聊天、草稿确认、我的工单 |
| 操作员工作台 | http://127.0.0.1:8020/operator | 登录并推进工单状态 |
| Dify 工作台 | http://127.0.0.1:8088 | 查看或编辑本地 Agent 图 |
| 业务健康检查 | http://127.0.0.1:8020/health | 确认业务应用启动 |
| Milvus | http://127.0.0.1:19530 | SDK 服务地址，非浏览器管理页 |
| Milvus 健康检查 | http://127.0.0.1:19091/healthz | 向量服务探针 |

Dify 账号与操作员口令见 **`dify/local/selfhost/本机访问说明.txt`**。这是被 Git 忽略的私有文件，不能截图上传或提交。模型密钥放在根目录私有 `.env` 中，至少提供 `EMBEDDING_API_KEY`；可单独提供 `LLM_API_KEY`。本地初始化只把相应凭证写入本地 Dify，不调用 Dify Cloud 或 Railway。

## 演示顺序

1. 输入“查询 JD2026003 的冷链温度异常，检索 SOP 并准备工单草稿，暂时不要建单”。
2. 核对回答中的订单快照和文件/章节依据；核对来自数据库的草稿卡片。没有卡片时不能把模型文字当成已生成草稿。
3. 点击“确认创建工单”，保存实际工单号；相同完整确认短语重复发送应返回原工单。
4. 用操作员口令登录，按 `open → processing → resolved → closed` 填写模拟处理备注。
5. 返回用户工单页，检查最新状态与四条状态事件；可在聊天中使用完整工单号查询。

订单只有四条历史模拟快照，工单处理为演示操作。用户页面是匿名 Cookie 会话，清除 Cookie 会失去这个浏览器的归属信息。

## 数据和配置在哪

| 数据 | 位置 |
| --- | --- |
| 业务 SQLite | 本机 Docker 卷 `logisupply-dify_business_data`，容器内 `/data/local-logisupply.db` |
| Dify 数据库、文件、插件与 Redis | `logisupply-dify_*` Docker 命名卷 |
| Milvus 与内嵌 etcd 数据 | `logisupply-milvus_milvus_data` Docker 命名卷 |
| 本地服务配置、账号、工作流与日志 | `dify/local/selfhost/`，全部 Git 忽略 |
| 可分享的编排源码 | `deploy/dify/`、`compose.rag.yml`、三个 PowerShell 入口 |

停止脚本仅停止这套本地项目与其 Milvus，保留数据。不要运行 `down -v` 或 Docker 卷清理，否则会删除对应持久数据。原有业务数据库和旧 Qdrant 数据保留；本轮新建的本机演示 SQLite 最初位于 Windows 目录，发现跨系统 WAL 访问的 I/O 错误后，已停应用并用 SQLite backup 迁入上述 Docker 卷，保留两张演示工单、八条事件及网页会话。旧文件留存但不再是运行库。旧 Railway 运行部署已按用户要求下线，项目、配置和 SQLite 卷保留；旧 Dify Cloud 未修改。二者都不参与当前本机运行。下线证据见 evaluation/results/railway_shutdown.json。

运行中的 SQLite 由 Linux 容器访问，不要用 Windows SQLite 程序直接打开其文件。需要核对数据时用页面/API，或在应用容器内使用 SQLite；备份应使用 SQLite backup API，避免复制未一致落盘的 WAL 文件。`deploy/dify/migrate_business.py` 是此次迁移辅助脚本，目标文件存在时拒绝覆盖，不属于每次启动流程。

## 重要连接关系

- 浏览器访问 `127.0.0.1:8020`；FastAPI 在 Docker 内访问 `http://nginx/v1`。
- Dify 工具访问 `http://logisupply-api:8018`，和页面共用同一个 SQLite。
- 本地网络 `logisupply-local` 的子网是 `172.29.240.0/24`，Milvus 别名为 `milvus-rag`。Squid 仅额外允许这个本地子网，避免误拦本机工具。
- Dify 的 Redis 密码必须与 `CELERY_BROKER_URL` 一致；沙箱密钥必须同时绑定 `SANDBOX_API_KEY` 和 `CODE_EXECUTION_API_KEY`。生成脚本已统一处理。
- 经典 Dify 代码节点请求沙箱时带网络能力标记，本地沙箱需保留官方网络开关；应用代码中的门控节点只执行字符串/JSON处理。
- Nginx 使用 Docker DNS 动态解析上游，避免 API 容器重建后沿用旧 IP。
- `LOGISUPPLY_ALLOW_LOCAL_DIFY_HTTP=true` 只用于允许回环和指定 Dify 容器端点，不会普遍放开外部 HTTP。

## 验证命令与边界

```powershell
.venv\Scripts\python.exe -m pytest
cd web
npm test
npm run build
cd ..
.venv\Scripts\python.exe evaluation/local_acceptance.py
```

最后一个命令会真实调用本地 Dify、模型 API 和工具，并创建后关闭一张模拟工单；输出 `evaluation/results/local_acceptance.json`。35 道检索开发题和 Python 模型工具测试的旧报告不能代替这个真实 Dify 验收；来源命中也不是回答准确率。初始化失败时先看私有 `startup.log`、`last-console-error.json`，不要将含凭证的完整日志贴入公开仓库。
